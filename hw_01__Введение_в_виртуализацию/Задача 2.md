Задача 2

Выберите один из вариантов платформы в зависимости от задачи. Здесь нет однозначно верного ответа так как все
зависит от конкретных условий: финансирование, компетенции специалистов, удобство использования,
надежность, требования ИБ и законодательства, фазы луны.

    Тип платформы:
    
    - физические сервера;
    - паравиртуализация;
    - виртуализация уровня ОС;

    Задачи:
    
    - высоконагруженная база данных MySql, критичная к отказу;
    - различные web-приложения;
    - Windows-системы для использования бухгалтерским отделом;
    - системы, выполняющие высокопроизводительные расчёты на GPU.
    - Объясните критерии выбора платформы в каждом случае.


Решение:

_1. Высоконагруженная БД MySQL, критичная к отказу
✅ Выбор: Физические серверы (Bare Metal)

Критерии выбора:

    - Производительность I/O - БД критична к задержкам дисковой подсистемы. На физическом сервере нет накладных
    расходов гипервизора на обработку дисковых операций, прямой доступ к NVMe/SSD RAID
    - Предсказуемость - Нет «шумных соседей» — другие ВМ не могут перехватить CPU-кэш, память или I/O каналы
    - Надёжность - Меньше слоёв абстракции = меньше точек отказа. При отказе гипервизора падают все ВМ сразу
    - Память - БД потребляет много RAM; на bare metal вся память доступна без оверхеда гипервизора

Допустимая альтернатива:

    - Паравиртуализация — если требуется High Availability (live migration, автоматический failover на другой
        хост). В этом случае выбирают гипервизор 1-го типа (VMware ESXi, Proxmox/KVM) с прямым пробросом дисковых
        контроллеров (PCIe passthrough) и выделенными ресурсами (CPU pinning, huge pages).

Почему не контейнеры:

    Контейнеры разделяют ядро ОС с хостом — при панике ядра упадут все БД. Кроме того, слабая изоляция I/O и
        сложности с управлением состоянием (stateful workload).


_2. Различные web-приложения
✅ Выбор: Виртуализация уровня ОС (контейнеры — Docker / Kubernetes)

Критерии выбора:

    - Плотность размещения - Контейнеры потребляют минимум ресурсов (нет гостевой ОС), на одном сервере можно разместить
        десятки микросервисов
    - Скорость развёртывания - Запуск контейнера — секунды против минут у ВМ. Важно для CI/CD и автоскейлинга
    - Изоляция зависимостей - Каждое приложение работает в своём окружении со своими версиями языков и
        библиотек, без конфликтов
    - Масштабируемость - Kubernetes позволяет горизонтально масштабировать сервисы по нагрузке
    - Стоимость - Нет лицензий на гипервизор, эффективное использование железа

Допустимая альтернатива:

    - Паравиртуализация — если web-приложения требуют разных ОС (одно на Linux, другое на Windows) или нужна
        усиленная изоляция (multi-tenant среда, разные клиенты).

Почему не физические серверы:

    Избыточно и дорого. Низкая утилизация ресурсов, долгое развёртывание, сложно масштабировать.


_3. Windows-системы для бухгалтерского отдела
✅ Выбор: Паравиртуализация

Критерии выбора:

    - Запуск Windows - Бухгалтерские программы (1С, клиент-банк, ЭДО) требуют полноценной Windows с GUI. Контейнеры
      Windows ограничены и не дают полноценного рабочего места
    - Управляемость - Централизованное управление парком ВМ: снапшоты, бэкапы, шаблоны, удалённый доступ
    - Изоляция и безопасность - Каждая ВМ изолирована; при заражении одного рабочего места остальные не
        страдают. Можно настроить политики ИБ на уровне гипервизора
    - Отказоустойчивость - Live migration при обслуживании хоста, HA при его отказе
    - Лицензирование - Возможность использовать корпоративные лицензии Windows Server + RDS (Remote
        Desktop Services) для терминального доступа бухгалтеров

Допустимая альтернатива:

    - Физические тонкие клиенты + терминальный сервер — если бухгалтеров много и нужна максимальная
        простота. Но это частный случай паравиртуализации (ВМ терминального сервера).

Почему не контейнеры:

    Windows-контейнеры не предоставляют полноценный GUI-рабочий стол, ограничены в поддержке десктопных приложений
        и не подходят для пользовательских рабочих мест.

Почему не физические серверы:

    Дорого, сложно обновлять и бэкапить, нет гибкости в распределении ресурсов.


_4. Системы, выполняющие высокопроизводительные расчёты на GPU
✅ Выбор: Физические серверы (Bare Metal)

Критерии выбора:

    - Прямой доступ к GPU - Для максимального быстродействия GPU должен быть доступен напрямую, без прослойки
        гипервизора. Любая виртуализация добавляет задержки в передаче данных PCIe
    - Производительность - Научные расчёты, ML/DL тренировки, рендеринг — задачи, где каждый процент
        производительности важен
    - Драйверы и CUDA - Прямая установка драйверов NVIDIA/AMD без ограничений виртуальной машины
    - Предсказуемость - Нет contention за ресурсы GPU с другими ВМ

Допустимая альтернатива:

    - Паравиртуализация с GPU passthrough (PCIe passthrough / SR-IOV / NVIDIA vGPU) — если нужна консолидация
        нескольких GPU-задач на одном сервере или требуется миграция ВМ. Современные гипервизоры (KVM, ESXi)
        поддерживают проброс GPU с минимальными потерями (~2–5%).
    - Контейнеры (nvidia-docker) — популярный вариант в ML/DL (Kubernetes + GPU-ноды). Контейнер получает
        прямой доступ к GPU через драйвер хоста, overhead минимален. Это компромисс между производительностью
        и удобством оркестрации.

Почему не «чистые» контейнеры без GPU-поддержки:

    Без специальной настройки (NVIDIA Container Toolkit) контейнер не увидит GPU.

Однозначного ответа нет — выбор зависит от приоритетов:

    Максимальная производительность → физические серверы
    Гибкость и управляемость → паравиртуализация
    Плотность и скорость развёртывания → контейнеры

В реальной инфраструктуре чаще всего используется комбинация платформ: bare metal для БД и GPU-кластеров,
    гипервизор для рабочих мест и сервисных ВМ, контейнеры для микросервисов и web-приложений. Это
    называется гибридная инфраструктура.
